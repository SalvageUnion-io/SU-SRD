1. Plan Review & Critical UX Feedback

What the Plan Gets Right

Pilot-centric navigation is the correct call. The existing builder's entity-type-centric approach (separate pages for pilots, mechs, crawlers) forces context-switching that breaks gameplay flow. A player thinks "I want to use my mech's railgun" -- not "I want to navigate to the mech page, find railgun, check its stats." The pilot sheet as hub, with mech/crawler inlined, matches how players actually think during sessions.

Tab-based organization for the lower content area is sound. Actions as the default tab is correct -- that is the most-used content during play. Mech, Pilot, and Crawler as secondary tabs match the frequency of access. The sticky top section with pilot header + mech strip keeps the critical "dashboard" always visible.

The Push flow design is thoughtful. Recognizing that Push is a dramatic decision point -- not just a UI button -- and designing a multi-step flow with heat consequences built in shows strong game understanding.

Using suref-react's existing Card/EntityDisplay patterns avoids reinventing proven components and keeps visual consistency with the SRD reference site.

Critical Issues

ISSUE 1: Sticky Header Height on Mobile Will Be Punishing

The plan puts both the Pilot Header (class art, callsign, HP/AP/TP) AND the Active Mech Strip (name, SP/EP/Heat bars with controls) in the sticky top section. On a phone in portrait, this will consume roughly 200-260px of vertical space:

  • Pilot header with image: ~120-140px
  • Mech strip with bars: ~80-100px
  • Tab bar: ~44px

That leaves only ~400px of scrollable content on a typical phone (812px viewport minus status bar, browser chrome, and the sticky block). This is borderline -- especially when the Actions tab needs room for card content.

Recommendation: The sticky section should be collapsible/minimizable. Two approaches:

  1. Auto-collapse on scroll: When the user scrolls down in tab content, the pilot header collapses to a single-line summary (callsign + HP/AP/TP as compact chips). The mech strip collapses to a single line (mech name + SP/Heat as compact chips). Scroll up to expand. This is the iOS contact-header pattern.
  2. Manual toggle: A small chevron/grip handle between the sticky section and tabs that lets the user collapse to a compact "instrument panel" view. Better for intentional control.

I recommend approach 1 (auto-collapse) because it requires zero additional cognitive load -- the player just uses the app naturally and gets more content space when they need it.

ISSUE 2: The "Actions" Tab Tries to Do Too Much

The plan describes the Actions tab as showing ALL actions from every source (chassis abilities, systems, modules, pilot abilities, equipment, crawler bays), organized by source groups. For a mid-level character, this could mean 15-25+ action cards with source headers.

Problems:

  • On mobile, even compact cards need ~80-100px each. 20 cards = 2000px of scroll.
  • Source grouping (Chassis, Systems, Modules, Pilot, Equipment, Crawler) makes mechanical sense but does not match how players think. A player thinks: "What can I do RIGHT NOW on my turn?" They want to see Turn Actions. Or: "I got hit, what Reactions do I have?"
  • The proposed search/filter bar at the top helps power users but adds UI weight and is slow on mobile (opening a keyboard covers half the screen).

Recommendation: Change the default grouping from "by source" to "by action type."

Primary filter: Action type chips (horizontal scroll, always visible):

[All] [Turn] [Reaction] [Free] [Short] [Long] [Downtime]

This matches gameplay flow: "It's my turn, show me Turn actions." "Enemy attacks, show me Reactions." The source is shown on each card as a small badge but is not the organizing principle.

Destroyed items should be filterable OUT rather than just "greyed out at bottom." During active combat, destroyed items are noise. But during downtime (repair phase), you want to see them. Add a toggle: "Show Destroyed" (off by default during play).

ISSUE 3: 3-Column Card Grid on Mobile is Not Viable

The plan repeatedly specifies "3-column card grid (matching official sheet)" for abilities, systems/modules, and crawler bays. On a paper sheet, the 3-column layout works because:

  • The sheet is landscape A4/Letter (~11 inches wide)
  • Cards are roughly 3.5 inches wide with readable text
  • You can see all 12 cards at once

On a phone (375px wide), 3 columns means each card is ~115px wide. At Fira Code monospace, that fits approximately 12-14 characters per line. Ability names like "EMERGENCY SHIELD BOOST" will not fit. Descriptions will be unreadable multi-line truncations.

Recommendation: Responsive grid strategy:

  • Mobile (< 640px): 1 column, full width. Cards are compact horizontal strips.
  • Tablet (640-1024px): 2 columns.
  • Desktop (> 1024px): 3 columns (matching the official sheet).

On mobile, the "card" becomes a horizontally-oriented strip: icon/badge on left, name + key info in center, condition/expand chevron on right. This gives each item a full ~350px of readable width.

ISSUE 4: The "Pilot" Tab Duplicates Information Already Visible

The plan puts class section, abilities, equipment, personal info, and notes all in the Pilot tab. But:

  • Pilot abilities are already shown in the Actions tab (as "Pilot Abilities" source group)
  • HP/AP/TP are in the sticky header
  • Class is in the sticky header

The Pilot tab becomes a reference/management tab (choose abilities, edit background text), while Actions is the play tab. This distinction is not clear to the user.

Recommendation: Rename the tab to "Build" or "Profile" to signal that it is for character management, not active play. Or: merge the pilot ability management INTO the Actions tab as an "Edit" mode toggle. During play you see your abilities as action cards; tap "Edit Loadout" to enter management mode where you can add/remove/reorder.

ISSUE 5: No Explicit "Roll d20" Surface Area

The plan mentions "Roll button accessible from the Actions tab and Mech Strip" but does not give it prominent placement. In Salvage Union, nearly every action requires a d20 roll. The roll button should be:

  • Always visible during play (not buried in a tab)
  • Large enough to tap confidently
  • Positioned in the thumb zone on mobile

Recommendation: A floating action button (FAB) in the bottom-right corner, always visible. It is the primary call-to-action of the entire app. Tap it to roll d20. The result appears as a bottom sheet / overlay, with the Push option immediately available. This FAB should use the orange pilot color (it is the player's action) and have a d20 icon.

ISSUE 6: Condition Cycling (Intact/Damaged/Destroyed) Has No Undo

The plan says "Tap system/module condition badge to cycle Intact->Damaged->Destroyed." Cycling is efficient but dangerous -- one accidental extra tap destroys an item. In a game where "my Auto-Loader got Destroyed" is a significant narrative moment, an accidental cycle from Damaged to Destroyed (when you meant to check its status) would be frustrating.

Recommendation: Use a long-press or 3-state toggle (like a segmented control) instead of tap-to-cycle. The segmented control shows all three states, the current one highlighted, and you tap the specific state you want. This is slower for intentional changes but immune to accidental taps. On mobile, the segmented control can be: 

[Intact] [Damaged] [Destroyed]
   ---     ===XXX

Where the current state has a visual indicator (filled/highlighted). Alternatively: tap opens a small popover/context menu with the three options. Slightly slower but zero-accident.

ISSUE 7: No Downtime/Session Workflow

The Quick Reference sheet has a detailed Downtime Procedure (tally salvage, pay upkeep, repair, craft, train, equip). This is a major gameplay phase that happens every session. The plan does not address this as a guided workflow.

Recommendation: Consider a "Downtime" mode or wizard accessible from the More (+) tab or as a long-press on the main FAB. This could step through: Tally Salvage -> Pay Upkeep -> Repair -> Train -> Equip. Not a blocker for v1, but worth noting as a Phase 2 feature.

ISSUE 8: Crawler Tab Scope is Unclear for Multi-Player Context

The plan mentions crawlers are shared resources with "Members" listed. But the Crawler tab on a pilot's sheet seems to show the full crawler editor (bays, scrap, storage). Questions:

  • Can multiple players edit the crawler simultaneously?
  • If Player A changes the Trading Bay NPC, does Player B see it?
  • Who "owns" the crawler for RLS purposes?

The plan says crawlers.user_id = owner. But bays are shared resources. If only the owner can edit, other players have a read-only Crawler tab, which limits its utility. If everyone can edit, the RLS policies need to be more nuanced.

Recommendation for UX: Show the crawler tab as read-only summary for non-owners, with a "Request Edit" or "Open Full Crawler" link that navigates to /crawler/$id. The full crawler view (Phase 5) is where multi-user editing happens. The inline tab should be a dashboard, not a full editor.

Minor Issues

  • Tab naming: "More (+)" is vague. Consider "Manage" or use a three-dot overflow icon instead of a tab. The "+" symbol suggests "create new thing," which is misleading.
  • Empty states not specified: What does the Actions tab look like when the pilot has no class selected and no mech? What does the Mech tab look like before a chassis is chosen? These first-run experiences need design. The plan should specify compelling empty states that guide the user toward the next step ("Choose a class to unlock abilities" / "Assign a mech to gear up").
  • Image upload on mobile: The plan includes image upload for pilot/mech but does not address the mobile UX for this. Camera vs gallery picker, crop interface, file size limits.
  • No keyboard shortcuts / desktop power-user features: Since this is mobile-first, fine for v1. But worth noting that desktop players at a laptop will want keyboard shortcuts for rolling (spacebar?), quick resource adjustment, etc.

3. Interaction Design Notes

3.1 Resource Tracking (+/-) on Mobile

Current pattern (from builder): NumericStepper with +/- buttons flanking a number. This works but has mobile-specific issues:

  • +/- buttons are small hit targets if the stepper is compact
  • No way to jump to a specific value quickly (e.g., "I took 5 damage")
  • Repeated tapping for large changes is tedious

Recommended interaction model:

  1. Primary: Tap +/- buttons. These should be minimum 44x44px touch targets. The number between them should be clearly readable. Use gap: 0 between button and number to keep the stepper compact but make the buttons themselves generously sized.
  2. Secondary: Tap the number itself to enter "direct edit" mode. The number becomes an input field with a numeric keyboard. Type the exact value, tap away to confirm. Critical for "I took 5 SP damage" -- the player calculates 8-5=3 and types 3, rather than tapping minus 5 times.
  3. Long-press +/- for rapid increment. Hold the minus button and the number decrements every 200ms. Release to stop. Middle ground between single tap and direct edit.
  4. Haptic feedback on each increment (if available via navigator.vibrate). Brief pulse confirms the tap registered, which matters when tapping quickly.
  5. Visual feedback: The number should briefly flash/scale when changed (a subtle 1.1x scale animation over 150ms). Confirms the change registered even in peripheral vision.
  6. Debounce saves at 300ms (per existing DEBOUNCE_TIMINGS.autoSave). Show a subtle saving indicator (small dot that pulses while saving, checkmark when saved). DO NOT block the UI -- optimistic updates are essential.

Layout for Pilot HP/AP/TP (mobile, expanded header):

Horizontal layout:
+--------+  +--------+  +--------+
| HP     |  | AP     |  | TP     |
|[-] 8 [+]  |[-] 3 [+]  |[-] 0 [+]
| /10    |  | /5     |  |        |
+--------+  +--------+  +--------+

Layout for Mech SP/EP/Heat (mobile, expanded):

Bar + stepper side by side:
SP: [========|-----] 5/8   [-][+]
EP: [===========|--] 4/6   [-][+]
HT: [===|--------] 2/4     [-][+]
     ^bar fills with color  ^44x44 targets

Heat % Bar Color Icon/Label

26-50% Yellow "!" badge
51-75% Orange "!!" badge
76-99% Red warning icon
100% Red + pulse glow skull/alert

3.2 Push Flow - Emotional Design

Push is the signature mechanic of Salvage Union. The UI should amplify tension without slowing the player down.

Timing and pacing:

  1. Initial roll result appears instantly (< 100ms animation).
  2. Push button is immediately available -- no delay. Player should feel agency.
  3. If the player taps Push, brief 300-500ms pause before re-roll appears. The d20 icon could spin/tumble during this beat. This builds tension.
  4. Re-roll result appears. If heat consequence triggers Heat Check, another 500ms beat before Heat Check prompt.
  5. Heat Check roll: same brief tension pause, then result.

Visual language:

  • Push button should be visually "dangerous" -- not red (which means error in UIs), but use the orange/amber palette with a slightly rough/industrial treatment.
  • Heat consequence preview ("2 -> 4 = AT CAP!") uses escalating color to match severity. At cap = red text. Safe headroom = calm green text.
  • Reactor Overload results get STRONG visual treatment: screen edge glow in red, the result text shakes slightly.
  • Successful Heat Check should feel like relief: red tension dissolves into calm green.

State management:

  • "Has pushed this roll" tracked to prevent double-pushing. Push button disappears after one push per roll. This is game-rules-enforced.
  • Model as a state machine: idle -> rolled -> canPush -> pushed -> heatCheck -> resolved. Use useReducer or small state machine. Prevents illegal state transitions.

3.3 Action Card Expand/Collapse

Collapsed state (default): Shows essentials for "is this the action I want?"

  • Name (bold, left-aligned)
  • Action type badge (right side, color-coded)
  • Source label (small, muted: "Everest Chassis" / "Railgun System" / "Engineer Core")
  • Cost indicator (AP/EP badge)
  • Condition badge (systems/modules only): colored dot or small segmented indicator
  • Expand chevron (right side)

Expanded state: Shows everything needed to USE the action:

  • Full description text (via EntityDisplay from suref-react)
  • Trait badges (Ranged, Ballistic, etc.)
  • Range badges (Close/Medium/Long/Far)
  • Damage value
  • "Roll for this action" button
  • For choice-based actions: player's chosen option highlighted

Interaction:

  • Use Chakra UI's Accordion component with allowMultiple: false
  • Entire collapsed card is the tap target (Fitts's law -- large targets are faster)
  • Smooth 200ms ease-out expand animation
  • Only one card expanded at a time to prevent overwhelming scroll height

3.5 Condition Toggling (Intact/Damaged/Destroyed) - Visual Design

Use a segmented control rather than tap-to-cycle to prevent accidental state changes:

Full variant (Mech tab, systems/modules):

Intact:    [*INTACT*] [ DAMAGED ] [DESTROYED]
              green      grey        grey

Damaged:   [ INTACT ] [*DAMAGED*] [DESTROYED]
              grey      amber        grey

Destroyed: [ INTACT ] [ DAMAGED ] [*DESTROYED*]
              grey       grey        red + strikethrough
  • Each segment: minimum 44px height for touch targets
  • Active state: filled with its color; inactive: ghost/outline
  • Destroyed item card: reduced opacity (0.5), faint red tint, name strikethrough
  • Damaged item card: use getTiltRotation() from suref-react for slight tilt

Compact variant (Actions tab, within action cards):

  • Green dot = Intact, Yellow/amber dot = Damaged, Red dot with X = Destroyed
  • Tapping the dot opens a small popover with the full segmented control
  • Dot has distinct shapes too: circle = intact, triangle = damaged, X = destroyed

3.6 Tab Navigation on Mobile

Scrollable tab bar -- Do NOT try to fit all tabs into viewport width. With 5 tabs (Actions, Mech, Build, Crawler, Manage), each needs ~70-90px. On 375px phone, that is tight.

  • Active tab: thick bottom border in entity color (orange for pilot context)
  • Inactive tabs: no bottom border, muted text
  • Horizontal scroll with momentum
  • Indicator gradient on right edge signals "more tabs available"
  • Tab bar is sticky (directly below header)

Tab persistence: When switching tabs, preserve scroll position within each tab. If player scrolled halfway down Actions, switched to Mech, and came back, they should be where they left off. Use React state for tab + scroll position.

Swipe consideration: Only implement tab-swiping if it does not conflict with inner horizontal scrolls (filter chips, cargo grid, stats row). Conflict detection is complex -- defer to Phase 2.

4. Accessibility Considerations

4.1 Color Contrast Analysis

The existing theme colors on backgrounds need verification:

Color RGB vs su.black (#282019) vs su.white (#FBF8F3)
su.orange 239, 137, 79 ~5.2:1 (AA pass) ~2.3:1 (FAIL)
su.green 122, 151, 138 ~3.6:1 (AA fail) ~3.3:1 (FAIL)
crawlerPink 206, 88, 152 ~3.7:1 (AA fail) ~3.2:1 (FAIL)
su.sicklyYellow 215, 195, 125 ~6.4:1 (AA pass) ~1.9:1 (FAIL)

Critical finding: Green (mech) and pink (crawler) colors fail WCAG AA contrast against both light and dark backgrounds. They cannot be used as text colors on their respective backgrounds.

Recommendations:

  • Use entity colors for backgrounds, borders, and decorative elements only
  • Ensure text always uses high-contrast foreground:
    • On orange bg: su.black text (~5.2:1, passes AA)
    • On green bg: consider darkening to rgb(80, 110, 95) for text-bearing areas, or use green only as border/accent with neutral backgrounds
    • On pink bg: use su.black text on lighter pink tint, or pink as border/accent only
  • For heat bar: never rely on color alone (see Section 3.1 for icon + color approach)
  • For condition indicators: each state needs color AND text label or distinctive shape

4.2 Touch Targets

WCAG 2.5.8 requires 24x24px minimum; mobile best practice is 44x44px.

Component Min Height Min Width Notes
Resource Stepper +/- 44px 44px Critical during play
Tab bar tab 44px 70px Full height tap target
Action card (collapsed) 60px 100% Entire card is target
Filter chip 36px auto 44px with padding
FAB (roll d20) 56px 56px Standard FAB size
Condition segment 36px 80px 44px with padding
Cargo grid cell 44px auto Min 44x44
Inline edit field 40px 100% Full field is target

4.3 Focus Management

  • Roll modal/bottom sheet: Focus must move to result area on open. On close, focus returns to trigger element (FAB or action card's Roll button). Use Chakra's DialogRoot with initialFocusEl and finalFocusEl.
  • Push flow: Each step traps focus within modal. Push/Keep buttons must be keyboard-navigable (Tab, Enter/Space).
  • Action card accordion: Expanding moves focus to expanded content. Collapsing returns focus to header. Chakra's Accordion handles this correctly.
  • Inline edit fields: Tap to edit moves focus to input. Blur or Enter saves and returns to display mode. Escape cancels and restores previous value.

4.4 Screen Reader Considerations

  • Resource values: aria-label="HP: 8 out of 10". Buttons: aria-label="Decrease HP" / aria-label="Increase HP".
  • Heat bar: aria-label="Heat: 2 out of 4 capacity. 50% full." At cap: add "AT CAPACITY. Heat check required on next turn."
  • Condition states: aria-label="Railgun. System. Condition: Intact." Segmented control uses role="radiogroup" with role="radio" per option.
  • Dice rolls: aria-live="assertive" on result area so screen readers immediately read "Rolled 14. Success."
  • Tab navigation: Chakra's Tabs provides proper ARIA. Verify aria-selected, role="tablist", role="tab", role="tabpanel".

4.5 Reduced Motion

Respect prefers-reduced-motion:

  • Dice tumble animation: replaced with instant result
  • Heat bar pulsing: replaced with static warning icon
  • Card expand animation: instant show/hide
  • Push flow tension pauses: eliminated, results appear immediately
  • Resource stepper scale animation: disabled

5. Summary of Recommended Changes

Must-Fix (Before Implementation)

  1. Collapsible sticky header - Auto-minimize on scroll to reclaim ~150px of viewport on mobile. The plan's fixed header will consume too much screen real estate.
  2. Action type filtering, not source grouping - Default the Actions tab to filter by action type (Turn/Reaction/Free/etc.) rather than group by source. Source is secondary info on each card.
  3. Responsive grid strategy - Replace all "3-column" specifications with responsive breakpoints: 1-col mobile, 2-col tablet, 3-col desktop.
  4. Floating d20 roll button (FAB) - Add a persistent, always-visible roll button in the bottom-right corner. This is the most-used action and needs permanent screen real estate.
  5. Condition change safety - Replace tap-to-cycle with segmented control or popover selection. Accidental state changes on systems/modules are too costly.
  6. Color contrast remediation - Green and pink entity colors fail WCAG AA. Use them as accents/borders only; ensure text always uses high-contrast foreground colors.

Should-Fix (High Value, Low Effort)

  1. Rename "Pilot" tab to "Build" or "Profile" to distinguish from play-focused Actions tab.
  2. Rename "More (+)" tab to three-dot overflow icon or "Manage" label.
  3. Design empty states for Actions (no class/mech), Mech (no chassis), Crawler (not assigned). First-run critical paths.
  4. Direct-edit on resource numbers - Tapping the number opens numeric input for quick jumps.
  5. Heat bar color + icon dual coding - Never rely on color alone for heat severity.

Nice-to-Have (Phase 2)

  1. Downtime workflow/wizard - Guided post-session procedure.
  2. Swipe between tabs - Natural mobile gesture.
  3. Haptic feedback on resource changes and dice rolls.
  4. Desktop keyboard shortcuts for roll, resource adjustment, tab switching.
  5. Roll history log - Collapsible log of recent rolls.
